One ecosystem. Three ways in.

Individual libraries stay useful on their own. The combined products will make a tested stack easier to install and run.

Available upstream

A library for your task

Install just the package you need, with its declared dependencies. Its imports, CLI, and version remain independent.

pip install varcodeSee Varcode on PyPI
Planned

A tested Python stack

An openvax metapackage will select exact, tested component versions. It adds dependency metadata, not duplicate library code.

pip install openvaxFuture interface; not published by this project yet.
Planned

A complete runtime

A Docker image will add locked Python dependencies and required system libraries. Use an image digest for a reproducible runtime.

ghcr.io/openvax/openvax2Model bundles, references, and user data stay explicit inputs.
Read the distribution design

Develop together.
Release independently.

One PR can update a producer and its consumers. Each package keeps its own tests, public API, dependency metadata, and version.

The release planner selects a package only when its version increases. A documentation change or another package’s release does not republish unchanged libraries.

Development guide

An illustrative coordinated change

varcodeVersion increasedRelease
isovarConsumer adaptedRelease after its bump
gtfparseVersion unchangedSkip

Update the metapackage separately when the new combination is tested. An OS-only fix can produce a new image revision without new Python releases.

The next step is migration.

Package PRs finish in their current repositories first. OpenVax2 already holds the design and version-selection tooling; package imports, publishing, and combined artifacts follow the migration plan.
